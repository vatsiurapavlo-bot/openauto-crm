# OpenAuto CRM — архітектура

Документ описує архітектуру всієї системи (розділи 1–19 ТЗ). Реалізовано поки Етап 1 —
див. [ETAPY.md](ETAPY.md).

## 1. Технології та чому саме вони

| Шар | Рішення | Примітка |
|---|---|---|
| Інтерфейс | React 19 + TypeScript, власний CSS-дизайн-систем, PWA | польською, адаптивний (комп'ютер, Android, iPhone) |
| Сервер | Node.js 22 + TypeScript, вбудований `node:http` | мінімум залежностей: `pg`, `zod`, `react` |
| База даних | PostgreSQL 16 | міграції на чистому SQL (`db/migrations`) |
| Збірка | esbuild | один крок: інтерфейс → `dist/public`, сервер → `dist/server` |
| Розгортання | Docker Compose: PostgreSQL + застосунок + Caddy (HTTPS) | перенесення на інший сервер — розділ 9 README |

### Відхилення від рекомендованого стеку (з поясненням)

ТЗ рекомендувало Next.js + Prisma + NestJS + Tailwind. Я свідомо обрав інше, і ось чому:

1. **Prisma → SQL-міграції + `pg`.** Найважливіші гарантії ТЗ (права доступу «на сервері й у базі даних»,
   незмінний Numer auta, заборона подвійного списання каси, незмінний журнал каси, аудит змін) реалізовані
   **всередині PostgreSQL** — через Row-Level Security, тригери, унікальні індекси та функції. Prisma не описує
   RLS-політики й тригери у своїй схемі, тож половина безпеки жила б поза ORM. Чистий SQL робить усе це
   явним, переглядуваним і перевіреним тестами.
2. **Next.js/NestJS → React SPA + легкий сервер.** CRM — це застосунок за логіном, йому не потрібен
   серверний рендеринг чи SEO. Простий сервер (~400 рядків) легше перевірити й перенести.
3. **Tailwind → власний CSS** з токенами (кольори, світла/темна тема). Результат той самий, без збірки Tailwind.
4. **Середовище розробки.** У середовищі, де писався Етап 1, не було доступу до npm-реєстру, тому Next.js і
   Prisma неможливо було встановити й **перевірити**. ТЗ забороняє видавати неперевірений код за робочий —
   тож вибір упав на стек, який можна було реально запустити й покрити тестами.

Якщо власник усе ж захоче Next.js/Prisma — схема БД залишиться тією самою (Prisma вміє `db pull`), а RLS і
тригери продовжать працювати незалежно від ORM.

## 3. Модель даних

Усі бізнес-таблиці мають `workspace_id` — **OpenAuto** зараз, **AB Auto** пізніше як окремий робочий простір
із власними авто, касою, витратами й користувачами (команда `npm run setup` з `WORKSPACE_CODE=ab-auto`).

```
workspaces ─┬─ workspace_members ── users ── sessions
            ├─ roles ── role_permissions, role_status_scope
            ├─ car_statuses (logistic | sales | settlement)
            ├─ cars ──┬─ car_finance (1:1, окремо — щоб RLS ховав фінанси)
            │         ├─ car_status_history
            │         ├─ files (фото / скани, Google Drive)
            │         ├─ documents ── counterparties
            │         └─ costs ── kasa_operations ── kasa_accounts (+ view kasa_ledger)
            ├─ countries, vat_rates, cost_categories, tax_rule_versions
            ├─ auctions ── auction_countries, auction_tariffs ── tiers, extra_fees
            ├─ auction_imports ── auction_import_fields, auction_price_history, purchase_calculations
            └─ audit_log, error_log, invitations, workspace_counters
fx_rates (спільні курси валют)
```

Таблиці модулів наступних етапів (Koszty, Kasa, VAT, Dokumenty, аукціони, імпорт) **вже створені** й захищені
RLS — щоб архітектура була цілісною й наступні етапи не ламали попередні.

### Ключові рішення

- **Numer auta** — `1, 2, 3…` окремо для кожного робочого простору. Присвоює тригер у БД з лічильника
  `workspace_counters`, який лише зростає: номери не повторюються після архівації, не змінюються після створення
  (тригер блокує зміну), не мають штучної межі (`bigint`). Внутрішні зв'язки — через прихований UUID.
- **Три виміри статусу** (п. 3 ТЗ): `logistic` (де авто), `sales` (продаж), `settlement` (розрахунок).
  Колір/рамка картки = статус розрахунку, якщо авто *Rozliczone*, інакше логістичний. Власні статуси й кольори —
  рядки в `car_statuses`. Кожна зміна потрапляє в `car_status_history` (дата, час, користувач) — тригером, тож
  її неможливо «забути» в коді.
- **Нічого не видаляється.** Роль застосунку не має права `DELETE` на бізнес-даних; видалення = `deleted_at`.
- **Одночасна робота кількох користувачів** — оптимістичне блокування: кожне авто має `version`; збереження зі
  старою версією повертає 409 «хтось змінив це авто — оновіть».
- **Гроші** — `NUMERIC(14,2)` у БД, BigInt-гроші в коді, рядки `"1234.56"` в API.

## 4. Безпека — три рівні

1. **Інтерфейс** приховує недоступні розділи (лише зручність, не захист).
2. **Сервер** перевіряє права для кожного запиту (`requirePerm`), валідує дані (`zod`), не повертає фінансові
   поля ролям без `cars.finance.view`.
3. **База даних (головний рівень).** Застосунок підключається роллю `openauto_app`, яка не є власником таблиць і
   не має `BYPASSRLS`. У кожній транзакції встановлюються `app.workspace_id` і `app.user_id`, а політики RLS
   самі вирішують, що видно:
   - інший робочий простір — невидимий;
   - `car_finance`, `costs`, `kasa_*`, `audit_log` — лише з відповідними правами;
   - роль *Serwis* бачить тільки авто в статусі *Serwis*, *Lakiernia* — тільки в *Lakiernia*;
   - тригер не дасть ролі без `cars.edit` змінити щось, крім статусу, а без `cars.settle` — розрахувати авто.

   Сервер у продакшені **відмовляється стартувати**, якщо роль БД обходить RLS.

Інше: паролі — scrypt; токен сесії лише в HttpOnly-cookie, у БД — тільки SHA-256; сесії відкликаються при
виході/зміні пароля/деактивації; обмеження спроб входу; захист CSRF (обов'язковий заголовок); CSP та інші
заголовки; HTTPS через Caddy; аудит входів і всіх змін (без хешів паролів).

## 5. Фінанси та податки (Етапи 3–4)

- Витрата з оплатою *Gotówka* → рівно одна операція в касі на кожну версію витрати (унікальний індекс
  `(cost_id, cost_version)` + ключ ідемпотентності). Редагування витрати → коригувальна операція, а не
  перезапис. Журнал каси незмінний (тригер). `saldo po operacji` рахується з журналу (view `kasa_ledger`), тому
  не може «роз'їхатися» після редагування.
- VAT-marża: `Marża = Cena sprzedaży − Kwota nabycia`, `VAT = MAX(0, Marża × 23/123)` — реалізовано в
  `shared/vat.ts` і перевірено на прикладі з ТЗ (1 687,23 zł). VAT naliczony не віднімається від маржі, а
  враховується в податковому періоді.
- Ставки й правила (VAT-marża, akcyza, PIT, składka zdrowotna) — у `tax_rule_versions` з датами чинності та
  статусом `do_weryfikacji` / `zweryfikowana` (потрібні ім'я та дата перевірки бухгалтером). Ставки акцизу, PIT і
  składki **не вписані** — їх має внести бухгалтер; система не вигадує чисел.
- *Zysk A / Zysk B* — налаштовувані сценарії прогнозу, не спосіб приховати операції.

## 6. Аукціони (розд. 15, 18)

- Окремий модуль `integrations/auctions`. Контракт `AuctionAdapter` **не має жодного методу запису** — ставки,
  покупки, повідомлення технічно неможливо виразити.
- OPENLANE, BCA, Autorola, AUTO1 внесені як *потенційні* платформи зі статусом API `niezweryfikowane`.
  Реальні адаптери — окремими етапами після перевірки офіційних API та дозволених методів.
- Кожне імпортоване поле зберігається з джерелом, датою й ознакою «підтверджене / автоматичне»; невідоме = NULL.
- Тарифи: аукціон × країна × період, ступінчасті пороги ціни, додаткові збори, ознака «орієнтовний».
  Тариф, використаний у розрахунку, не можна змінити (тригер) — лише створити нову версію.
- Країни реєстрації, місцезнаходження, продавця й рахунку зберігаються окремо.

## 7. Розгортання, Google Drive і резервні копії

**Railway:** Dockerfile → `node dist/server/start.js`: міграції з `DATABASE_URL` (власник схеми) → роль
`openauto_app` (без BYPASSRLS; пароль = HKDF з пароля `DATABASE_URL` — стабільний між розгортаннями й не залежить від `OPENAUTO_MASTER_KEY`, див. `src/server/db/app-role.ts`) →
перший власник зі змінних `BOOTSTRAP_*` (лише якщо в базі немає користувачів) → сервер, що обслуговує
запити роллю `openauto_app`. Адмін-з'єднання залишається в пам'яті лише для копій і токена Drive
(таблиці `system_integrations`, `backup_runs`, `system_settings` недоступні ролі застосунку на запис).

**Google Drive:** OAuth 2.0, область `drive.file` (лише файли, створені CRM). Refresh-токен зашифрований
AES-256-GCM (ключ з `OPENAUTO_MASTER_KEY`, мета «token»). Параметр `state` підписаний HMAC і прив'язаний до
сесії. Підключає/відключає лише власник головного робочого простору.

**Копії:** `pg_dump -Fc` → AES-256-GCM (мета «backup») → `OpenAuto CRM/Backups/*.oabak` → залишаються 60
останніх. Планувальник у процесі сервера (щодня після 2:00 за Варшавою, лише в середовищі `production`),
захист від паралельних запусків — advisory lock у PostgreSQL. Додатково — знімки томів Railway.

**Запуск з реальними даними:** перевірки (HTTPS, cookie, роль БД, пароль власника, ключ, Drive, свіжа
копія, розклад) + три ручні підтвердження → запис у `system_settings` і журналі. До цього — банер «Tryb testowy».

**CI/CD:** GitHub Actions (`.github/workflows/ci.yml`) на кожен push і PR; Railway «Wait for CI» розгортає
`main` лише після успіху. Правила для Claude — `CLAUDE.md` (лише гілки й PR, Merge робить власник,
міграції лише додавальні, щоб відкат Railway був безпечним).

Excel (експорт/імпорт) — Етап 5; таблиця `files` уже передбачає зберігання фото й документів у Drive.
